### R12-1（blocker）：门控必须统计全部**非终态**任务 ✅ 已修

- **缺口**：原判据只看 `pending/retrying`。多 worker 下任务被 claim 后即离开这两个状态，于是"`pending/retrying` = 0"**不等于**"我是批次最后一个活动任务"，会误判队列已空并重复全站刷新。
- **对齐到本项目真实状态值（交叉校验）**：`publish_jobs.status` 的 CHECK 是 `pending|processing|completed|failed|retrying|cancelled` —— **没有 `running`**；L1 说的 "running" 在本项目就是 **`processing`**。仓库也没有统一的 `TERMINAL_STATUSES/ACTIVE_STATUSES` 导出（各文件内联 `IN (...)`），故未引入第二份状态枚举。
- **修法**：`shouldRefreshSiteNow(jobId)` —— **排除当前任务**、统计 `pending|processing|retrying`：
  ```ts
  const active=Number((await query("SELECT count(*) AS n FROM publish_jobs WHERE id<>$1 AND status IN('pending','processing','retrying')",[jobId]))[0].n);
  return active<=PUBLISH_QUEUE_THRESHOLD;
  ```

### R12-2（契约）：`PUBLISH_REFRESH_MAX_DEFER_MS` **不是** wall-clock SLA ✅ 已改准确

按 L1 给的选项 **B**（本轮目标只是解决大批量 O(N²)，不引入持久化 scheduled rebuild）。代码注释已改写为准确口径：

> 它是 **active-queue defer interval** —— 只在「有新的发布任务经过本门控」时才会被检查。若最后一个任务失败/被取消/死信而再无任务进入，站级产物（列表页/首页/sitemap/manifest）会一直停在上次刷新，**不会自己触发**。若将来产品契约要求严格上限，必须升级为持久化的 delayed rebuild job，而不是模块级时间戳。

## 2. 为什么改（实测证据，不是推测）

**O(N²) 根因链**（2026-10-02 实测）：
1. `processPublishJob` **每个任务**都调 `refreshSite()`；
2. `refreshSite()` 会**对全部 9 个启用语言、把 `published_documents` 里每一条文档逐条重渲染 + 重写 HTML + 重建全部 sitemap** → 单任务耗时 **∝ 已发布总数 N**；
3. `processPublishJob` 全程持 `pg_advisory_lock(837611,1)` → **所有发布任务全局串行**（**提高 worker 并发无效**）。
4. 观测量：同一批次每小时完成数 **284 → 372 → 229 → 158 → 125 → 106 → 53**，速率单调衰减；剩余 1602 条按 O(N²) 外推 **≈26.7 小时**（原估"4 小时"）。

**连带second-order 影响**：该查询风暴 × PG `log_statement=all` → **单日 PG 日志 11 GB**，prod 磁盘涨到 **95%（仅剩 2.2G，ETA 161 分钟写满）**。已于 2026-10-02 18:05 处置（截断日志 + `log_statement='none'`，实测增长归零、磁盘回到 68%）。

**幽灵发布复发链（E-11 → E-12）**：裸 SQL 删内容行会绕过 `remove()` 的 unpublish 入队 → `published_documents` 留下幽灵路由 → 而**它才是事实源**，每次 rebuild 都会把幽灵页重新生成。原修法是手工补 unpublish（一次性），本改动把它变成**机制**。

## 4. 诚实标注的边界（取证脚本作者与 L2 一致确认）

1. **冷启动例外（代码语义，非缺陷）**：`lastSiteRefreshAt` 模块级初值为 `0` → `Date.now()-0>=5min` 恒成立 → **进程内第一次**门控求值必刷新。常驻 worker 里表现为"重启后第一个任务立即刷新，其后在批量中才延迟"。取证时若只看进程首任务会误得"没有延迟"。
2. **判别物的选择**：单看 `/zh/index.html` 的"未变"理论上可能被 `writeDocument` 的 checksum 短路解释，故以 `manifest.json`（含 `generatedAt`+`jobId`，每次 refreshSite 必变）为**主判别物**，deferred 日志为第二重证据。
3. **一次 Windows EPERM**：第一轮取证时 `writeAtomic` 的 rename 被占用文件拦住（`zh/products/page/2/index.html`），该 unpublish 任务落 `retrying`；加重试后二/三/四轮未复现。**属环境层文件锁**，但说明 refreshSite 遇文件占用会让整轮站级刷新失败（此时 job 落 `retrying` 可重放）。
4. **取证的副作用**：每次 `rebuildSite` 会 UPDATE 既有 90 条 `published_documents` 的 `snapshot/job_id/published_at`（行数不变）—— 等价于线上点一次「重建已发布站点」。

**已核实「不是缺口」的一项**（避免给 L1 喂伪命题）：`site_paths` 由触发器 `guard_site_path()` 维护（[011_runtime.sql:18-19](../database/011_runtime.sql)）—— 行 DELETE 与被软删（`deleted_at IS NOT NULL`）都会自动清行，故**不存在"幽灵路由清掉了但 site_paths 残留"的问题**。
