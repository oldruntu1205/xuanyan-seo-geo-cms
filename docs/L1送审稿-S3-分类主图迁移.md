### 2.6 实测发现的两条事实（请一并判断，见 Q1/Q6）

- **事实 A（背景事实，不是裁决依据）**：`012_operational_defaults.sql` 的注释写「每个外键都建索引」，但 **013–029 都没有再补** `ix_fk_*`。本机 dev 库实测：public 下 **230 个外键中 68 个没有首列索引**（含 029 自己新增的 `inquiries.intent_override_by`）。
  > **订正（L1 终审 2026-10-09）**：采纳「030 只加列 + 外键、不补索引」的依据是**当前分类表规模小、暂无相关性能证据**，「其他外键也没索引」只是背景事实，**不能当作理由**（否则等于用既成事实为新增例外背书）。审查记录按此口径订正；已应用的 `030` 迁移文件**不改**（改已登记迁移会让 runner 抛 `Applied migration changed` 并中止发布）。
- **事实 B**：用户对分类图的原始要求是 **4:3**，但 S5 的 Q5 裁决把**卡片主图统一为 1:1**（`.card-art`），分类卡与产品卡共用 `card()`，所以现在分类图也是 1:1。本切片**未动任何 CSS**。**该原始要求记为「已知差异 / 未完成」，需用户确认后再开切片**（L1 终审：不得标记为已完成，也不得仅凭其它切片的裁决代用户取消）。

## 三、逐条待判问题（请逐条回，可只回编号）

**Q1 — 030 不补 `ix_fk_*` 索引，是否可接受？**
理由（**已按 L1 终审订正**）：当前 `taxonomy_terms` 规模小、且没有任何相关性能证据；**不以「其他外键也没索引」为理由**。选项：(a) 接受「本迁移只加列+外键」；(b) 要求 030 内补一条 `ix_fk_*`（则本切片多一个可回滚对象）；(c) 另开一个「表级索引整理」迁移恢复 012 声明的不变量。

**Q2 — 分类图 alt 的取法是否可接受？**
改动落在**通用**的「父表主图」分支上（`row.parent.featured_media_id`），所以 `content_items`/`products` 在「没有图库行」时**也会**获得当前语言的 `alt_text`。请判定：(a) 接受（语义更正确：`media_assets` 本来就没有 alt，alt 只能在按语言的翻译表）；(b) 只允许 taxonomy 分支 join alt；(c) 其他。**注意副作用**：这会让内容页/产品页的 `<img alt>` 在「有 alt 翻译」时从「标题兜底」变成译者填写的文案（DOM 属性值变化，不新增/删除节点）。

**Q3 — 回滚脚本的形态是否足够？**
现状：`DROP CONSTRAINT IF EXISTS` 后 `DROP COLUMN IF EXISTS`，注释明确写「DROP COLUMN 会丢所有已配好的分类主图关联，生产执行前必须备份 `taxonomy_terms`；首选向前修（出 031）」。请判定：措辞与做法是否满足本项目对「不可逆回滚」的要求，是否需要附加「备份校验」步骤。

**Q4 — 命名是否在契约内？**
列 `featured_media_id`（与 `content_items`/`products` 同名同形）、约束 `fk_terms_featured_media`、文件名 `030_taxonomy_featured_media.sql` + `rollback/030_taxonomy_featured_media.down.sql`。有无需要改名的理由（例如约束名统一前缀 `fk_` vs 既有 `*_fkey` 混用）。

**Q5 — 后台标签落点是否越界？**
规范原文写 `field-meta.ts` 补 `fieldLabels.featured_media_id='分类主图'`。但 `fieldLabels` 是**全局**列名表，照字面改会把 `products`/`content_items` 的同一列也改名成「分类主图」。故改为 `tableFieldLabels.taxonomy_terms`（该文件自带的按表覆盖机制）。请判定：这属于对规范的正确解释，还是要求严格照字面执行（会把产品主图也改名）。

**Q6 — 分类图 4:3 与现行 1:1 的冲突（事实 B）如何处理？**
本切片只交付「字段 + 装配 + 后台可编」，**分类卡比例仍是 S5 的 1:1**。请判定：(a) 接受，比例另开 CSS 切片；(b) 必须在本切片内给分类卡单独 4:3（则需改 `kiln-extra.css` 并重量基线）。

**Q7 — 上线前的前置要求（本切片不含生产动作）**
已知：老代码 + 新 schema 的兼容面只有「多一列」（`SELECT *` 与 `to_jsonb(p)` 都不受影响；`documents.ts` 是同一提交）。请判定：上线清单是否需要额外的检查项（例如执行前 `taxonomy_terms` 计数/备份校验、应用后 `migrate.mjs status` 断言、静态产物是否需要重建）。
