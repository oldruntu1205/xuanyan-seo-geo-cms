# 产品资料补录与发布操作单（C-1 / C-2）

> 用途：把站点从「1 个 `draft` 产品、0 条已发布产品译文、公开站询价单选不到产品」修到「目标语言下可询价、可被搜索引擎收录」。
> 日期：2026-09-30 ｜ 依据：**实际代码 + 本机演示库实测**（非推测）｜ 对应清单 C-1 / C-2

## 1. 判定规则（先记住这一条，否则会白忙）

公开站「询价单里能选到这个产品」的**唯一条件**是下面这条 SQL 命中 —— 见 [`apps/cms/src/server/api.ts:73`](../apps/cms/src/server/api.ts#L73)：

```sql
SELECT p.sku,p.id,t.name,t.order_unit FROM products p
JOIN product_translations t ON t.product_id=p.id AND t.locale_id=$2
JOIN published_documents d ON d.entity_id=t.id AND d.entity_type='product_translations'
WHERE p.id=$1 AND p.deleted_at IS NULL
```

命中不到 → `throw new DomainError('Product is unavailable')` → **HTTP 400**。

由此推出三条最容易踩空的结论：

1. **按语言判定**：zh 有已发布译文 ≠ en 有。只补中文，`/en` 站点照样选不到产品。
2. **`products.status` 不参与这条判定**：决定成败的是 `product_translations` 有没有进 `published_documents`。**"保存译文" ≠ "发布译文"**。
3. **`publish_status='draft'` 也选不到**：机翻草稿停在 `review`/`draft` 时，译文存在但未发布 → 依然 400。

## 3. 需要先准备的资料（C-2 的输入）

**产品级（所有语言共用）**：`sku`、`model`、`brand`、`material_code`、`capacity_value`+`capacity_unit`、`weight_value`+`weight_unit`、长/宽/高 + `dimension_unit`、`min_order_quantity`、`lead_time_days`、主图 `featured_media_id`

**每个语言一份**（至少 zh；其余语言可机翻后人工审核）：`name`、`short_description`、`description`、`features`、`applications`；采购资料译文 `order_unit`、`packaging_details`、`customization_details`、`sample_policy`

> `slug` / `path` 由系统生成，不必手填。`features` / `applications` 是 JSON 数组。

## 5. 本机演练：能做与不能做

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 判定 SQL 量化现状 | ✅ 可 | `.runtime/probe-rfq-availability.mjs`（只读） |
| 复现「某语言选不到产品」 | ✅ 已复现 | 见 §2 本地表（7 个语言为 0） |
| **机翻** | ❌ **本机不可用** | 本机 `.env` **没有 `TRANSLATION_API_KEY`**（prod 有，见 §17）。本地演练只能走「手工填译文」路径 |
| 用 psql 查/改 | ❌ 本机没有 psql | `.runtime` 的嵌入式 PG 只带 `pg_ctl.exe`/`postgres.exe`，**不带 `psql.exe`** → 本机一律用 node 探针（`.runtime/probe-*.mjs`） |
| 发布后快照翻转（0→1） | ⚠️ 需 worker 在线 | `published_documents` 由 **worker** 消费 `publish_jobs` 生成 —— 只调 API/domain 不启 worker，快照不会出现（这正是"发起了发布 ≠ 已发布"） |
| 端到端（选产品 → 提交 201） | ⚠️ 需起本地栈 | 已有脚本 `.runtime/smoke-rfq.mjs`，但需 `next start` 在 3001 + Redis + worker |

**结论**：本机可以演练**除机翻外的全部环节**。要真正走一遍端到端，需要：起本地栈（**`pwsh -File infrastructure/scripts/local-demo.ps1`**；⚠️ 是 `.ps1`，用 `node` 跑会报 `ERR_UNKNOWN_FILE_EXTENSION`）+ 一段**内容**（真实资料，或明确标注 `[演练]` 的演示文案）。

## 6. 回滚

| 改了什么 | 怎么回滚 |
| --- | --- |
| 产品资料 / 译文（内容层） | `/manage` 改回或删除；有版本历史与审计 |
| 发布（产生了快照与静态产物） | 用 `publish_jobs` 的 `unpublish`，或恢复 `static-site` 备份 tar；DB 用 `pg_restore` 恢复第 0 步的 dump |
| 迁移 | **本轮不需要任何迁移**（022/023 早已应用） |

## 7. 已知坑（本项目实测）

- **发布 ≠ 保存**：`/manage` 保存只写草稿；必须点「发布」并等 `publish_jobs` 完成，公开站才会变。
- **改 `packages/ui` / `packages/publisher` 后必须全站重建**，否则公开页仍是旧版（与产品翻译是两条独立的链）。
- **每语言都要有记录**：前台部分查询用**内连接**（案例：轮播 `hero_slides ⋈ hero_slide_translations`），漏填某语言 = 该语言下直接不显示。
- **SSH 里跑 SQL 一律 `psql -f -` + heredoc**：内联引号会**静默返回错误结果**（本项目已误判过两次）。
- **占位文案熔断不要绕过**：`publish-translations.sh` 的闸门就是防止「这个是量筒」进 8 个语言的公开页与 sitemap。

| --- | --- | --- |
