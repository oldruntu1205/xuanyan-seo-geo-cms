# 后台易用性改造方案：新手模式 + 任务向导

> 目标：让「小白客户」与「内部运营」都能轻松上手，教育成本从「培训几天」降到「打开就会」。
> 状态：方案文档（待评审）。评审通过后按「分期落地」逐期实施。
> 关联：`_deploy/DEPLOY-PROD.md`（生产部署）、`apps/cms/src/app/(console)/manage/`（后台实现）、`packages/domain/src/registry.ts`（资源/权限/发布机制）。

---

## 0. 一句话结论

后台的复杂不是「功能太多」，而是 **入口按资源表组织、发布机制对用户隐形、缺客户角色**。
用三招解决：**角色裁剪**（客户只看得到 20%）→ **任务向导**（隐式流程串成 checklist）→ **双模式导航**（新手/完整切换）。全部建立在现有权限与向导代码之上，改动是「收敛」而非「推倒重来」。

---

## 1. 现状诊断（结合代码，非空泛）

### 1.1 复杂度来源

| # | 根因 | 代码证据 | 对小白的影响 |
|---|---|---|---|
| 1 | 入口按「资源表」而非「任务」组织 | `HomeDashboard.tsx` 四区 + `page.tsx` 左侧「日常工作」平铺十几个 desk | 想「发产品」却看到 `translation_jobs`、`review_workspace` |
| 2 | 发布机制两套、对用户隐形 | `registry.ts:8-9` 的 `recordPublishable`（单条发布）vs `rebuildRequired`（全站重建） | 最大困惑源：改了内容首页没变 |
| 3 | 缺「客户」角色，角色粒度不够 | `registry.ts:26` `roleGroups` 只有 admin/editor/seo_manager/translator/reviewer；`canRead` 对非 admin 隐藏 `leads` | 要么给 admin（全量），要么给 editor（看不到询盘） |
| 4 | 术语黑话 | GEO、SLA、RFQ、incoterm、`review_workspace`、`translation_jobs` | 每个词一道门槛 |
| 5 | 通用表单 250 字段全铺 | `field-meta.ts` 中文化但仍是通用 CRUD 表单 | 分不清必填/可选 |

### 1.2 已有地基（可复用，不推倒）

| 已有能力 | 位置 | 复用处 |
|---|---|---|
| 角色/权限体系（roles、permissions、user_roles、role_permissions） | `registry.ts` + `cms-admin-users` | 角色裁剪直接加角色即可 |
| 工作台四区（按场景分组） | `HomeDashboard.tsx` | 新手模式沿用其「任务卡」视觉 |
| 新建内容向导（EntryWizard） | `page.tsx` 的 `EntryWizard` | 任务向导的雏形，扩成完整链路 |
| 字段中文化 + 提示 + 资源指引 | `field-meta.ts` | 术语/空状态在此扩展 |
| 专用编辑器（产品采购、产品图库、图片 ALT） | `ProductTradeEditor.tsx` 等 | 向导内复用作「步骤」 |

## 2. 目标信息架构

### 2.1 双模式

| 模式 | 默认给谁 | 看到什么 | 切换方式 |
|---|---|---|---|
| **新手模式** | `client` 角色 + 首次登录者 | 5 张「任务卡」+「我的内容」+「我的询盘」，无资源表列表 | 顶栏「切换完整模式」，用 `localStorage` 记忆 |
| **完整模式** | `admin` / `super_admin` | 现有工作台四区 + 高级管理 | 顶栏「切回新手模式」 |

新手模式的 5 张任务卡（对应高频场景，其余全部隐藏）：

| 卡片 | 任务 | 背后串联的资源 |
|---|---|---|
| 发布产品 | 从图到上线一次走完 | `products`/`product_translations` + `product_media` + `product_documents` + `translation_jobs` + `publish` |
| 发布文章 | 写内容→配图→多语→上线 | `content_items`/`content_item_translations` + `content_blocks` + `media_assets` + `publish` |
| 修改首页 | 换轮播图/改标题/改联系方式 | `hero_slides`/`hero_slide_translations` + `site_settings`/`site_setting_translations` + `rebuild` |
| 查看询盘 | 新询盘置顶、一键回复、状态跟进 | `inquiries`/`inquiry_items` |
| 我的内容 | 已发布的页面/产品，一键改 | `content_item_translations` + `product_translations`（只读自己可写的） |

### 2.2 角色裁剪（新增 `client` 角色）

在 `registry.ts` 的 `roleGroups` 增加一个白名单角色，只放开客户真正需要的组：

```ts
// 提案（示意，最终以 canRead/canWrite 的组白名单实现）
client: ['content', 'product', 'media', 'appearance']  // + leads.read 单独放开
```

关键调整点：

1. **放开 `leads` 的读权限**给 `client`：现有 `canRead` 对非 admin 一律隐藏 `leads`（`registry.ts:28`），需改为「`client` 可读 `leads`，但只读自己的询盘」。
2. **收紧**：`client` 不接触 `seo` / `translation`(高级) / `publishing`(手动重建) / `system` / `history`。翻译与重建由向导在后台自动执行，用户无感。
3. **保留内部角色**：`editor` / `seo_manager` / `translator` / `reviewer` / `admin` 不变，完整模式照旧。

> 设计原则：**不是把复杂功能做简单，而是把客户用不到的功能藏起来**。80% 复杂度在客户侧直接消失，无需重写任何业务逻辑。

### 2.3 渐进式暴露

新手模式只给核心；随熟练度（或用户主动点「高级」）逐级解锁。完整模式始终是「逃生舱」，保证不丢功能。

## 3. 任务向导设计（核心）

> 通用原则：向导 = 把 `recordPublishable` 与 `rebuildRequired` 的差异**收进最后一步**，用户全程只点「下一步」，最后一步统一叫「上线」。

### 3.1 向导通用骨架

```
步骤 1：基本信息（语言、标题/SKU）
步骤 2：正文 / 参数（正文、配图、采购资料）
步骤 3：多语言（可选，机翻 + 预览）
步骤 4：上线（内部自动：单条发布 + 触发重建，显示进度）
```

每一步右侧有「进度 checklist」和「这步在做什么」一句话说明；任一步可跳过（标「可选」）。

### 3.2 发布产品向导（8 步 → 用户视角 4 步）

| 用户看到的步骤 | 内部串联的现状操作 | 现状痛点 | 向导化后 |
|---|---|---|---|
| ① 基本信息 | `EntryWizard`（语言/SKU/名称） | 已有 | 沿用 |
| ② 产品资料 | `ProductTradeEditor`（MOQ/交期/包装/定制/样品政策/incoterm） | 字段多、必填不清晰 | 只暴露 3–5 个必填，其余折叠「高级」 |
| ③ 产品图片 | `ProductImagesEditor`（媒体库选图） | 要先去媒体库上传 | 向导内嵌「拖拽上传 → 自动入库 → 选封面」 |
| ④ 多语言 | `translation_jobs`（机翻草稿） | 要手动去「翻译工作流」 | 一键「生成其他语言草稿」，草稿态自动进审核 |
| ⑤ 上线 | `requestPublish`（单条发布）+ `rebuild`（重建） | **两套机制、用户分不清** | 合并为一步「上线」，内部自动判断 `publishModeFor()` |

### 3.3 发文章向导

```
① 类型（文章/页面/案例…）+ 语言 + 标题
② 正文（富文本）+ 配图（拖拽上传）
③ （可选）多语言机翻
④ 上线（内部：单条发布 + 若需进首页/导航则重建）
```

### 3.4 查看询盘（非向导，是「简化的询盘工作台」）

现状 `CrmDesk` 是通用 CRUD，小白要自己找「新询盘、怎么回、怎么标跟进」。改为：

- **新询盘置顶**（按 `created_at`，未读高亮，含 `first_response_at` 为空的 SLA 提醒）；
- **一键回复**：预置 2–3 条回复模板，点一下填入，改两句即发；
- **状态流转**：待回复 → 已回复 → 已报价 → 成交，用下拉选择而非看字段；
- 隐藏 `inquiry_items` / 附件等高级信息到「详情」折叠。

## 4. 发布机制统一（关键改动）

这是「改了内容首页没变」的根治。方案：

1. **抽象一个 `publishAll()` 门面**：输入资源表名，内部用 `publishModeFor()` 判断是 `record` 还是 `rebuild`，自动执行对应动作，并返回「哪些页面已更新」的提示。
2. **向导/任务卡最后一律走 `publishAll()`**，用户不再接触「发布」和「重建」两个按钮的区别。
3. **保留**完整模式里的「重新生成已发布页面」高级按钮（内部运营仍需要手动重建能力）。

> 不改 `packages/domain` 的发布语义（`record` vs `rebuild` 是正确设计），只在其上盖一层「用户无感」的门面。

## 5. 术语 + 空状态 + 表单（低成本高感知）

### 5.1 术语口语化（在 `field-meta.ts` 补一张「黑话→白话」映射，导航 label 用它）

| 现状 | 新手模式显示 |
|---|---|
| GEO 监测 | 搜索表现 |
| `review_workspace` | 待审核 |
| `translation_jobs` | 翻译进度 |
| `growth_workspace` | 内容建议 |
| incoterm | 贸易条款 |
| SLA（首响时限） | 回复时效 |

### 5.2 空状态引导（每个空列表给「下一步」）

现状空列表是空白。改为：每个资源空状态渲染一张「引导卡」——「还没有产品 → [发布第一个产品 ↗]」直达对应向导。

### 5.3 表单必填/可选分离 + 智能默认

- 通用表单默认「新手视图」：只显示必填 + 最常用可选；「完整字段」折叠进「高级」。
- 智能默认：语言默认当前站点主语言；`sort_order` 自动递增；`status` 默认草稿。

## 8. AI 驱动向导（2026-09-30 用户补充，核心机制）

> 用户明确：系统已内嵌 AI Agent，要充分利用——「发布新闻」用 Agent 直接生成草稿，用户只改需要改的地方，然后一键发布。
> 这使「任务向导」从「手工填表」升级为「AI 生成 → 人审核 → 一键发布」，教育成本进一步趋近于零。

### 8.1 现有 AI 地基（已核实，无需重做）

| 能力 | 位置 | 现状 |
|---|---|---|
| 一句话主题 → 完整文章草稿（标题/导语/分段落正文/SEO 标题摘要） | `AIWriting.tsx` + `domain/ai-writing.ts` 的 `generateWriting` | **已有**，草稿可逐字段编辑，带「01 提供资料 → 02 校对草稿 → 03 保存后发布」三步 UI |
| 对已有内容生成可审核的修改方案 | `AgentDesk.tsx` + `domain/ai-agent.ts` | 已有（读内容 → SEO 检查 → 方案 → 批准 → 套用） |
| 草稿落库 | `saveWritingDraft`（生成 `content_items` + `seo_metadata` + `content_item_translations`） | 已有，但 `status='draft'` |

### 8.2 断掉的一环 + 打通方案

**断点**：`saveWritingDraft` 保存后是 `draft`，发布是独立动作（`requestPublish`），且需 `publishing.write` 权限——所以「AI 生成草稿」后用户还得跳去「页面与文章」手动点发布。

**打通（三件事）**：
1. **前端 `publishAll()` 门面**：封装「保存草稿 → `requestPublish`（record 单条发布）→ 需要时 `rebuildSite`」，用户只点一次「上线」。
2. **`AIWriting` 增加「保存并发布」**：save 拿到 `{id, resource:'content_item_translations'}` 后立即走 `publishAll`，不再「保存完跳走」。
3. **「发产品」同理新增 AI 生成**：复用 `callLLMChat` 生成产品名/描述/特点/应用，落成 `product_translations` 草稿后一键发布。

### 8.3 权限决策（关键，影响 client 角色设计）

`requestPublish` 与 `rebuildSite` 都校验 `publishing.write`（或 admin/super_admin/reviewer 角色）。当前「发布」是审核员/管理员专属，`editor` 只能存草稿等审核。

对「小白自助」场景，**决策：给 `client` 角色授予 `publishing.write`**，理由：
- 「发布自己发的内容」是客户核心权利，不应卡审核；
- `rebuildSite` 只是重渲染公开页，不删数据、不危险，客户触发无害；
- 这是让「AI 生成 → 一键发布」闭环成立的前提。

> 代价：客户绕过了「四眼审核」。若某些客户仍需审核，可在「套餐/角色」之上再挂一层开关（见第 9 节遗留项 4），一期先按「自助发布」做。

### 8.4 用户旅程（改造后）

「发新闻」：点「发文章」卡 → 一句话主题 +（可选）关联产品 → AI 生成完整草稿 → 逐处修改 → 点「上线」→ 完成并给出公开页链接。全程无「字段/翻译/发布/重建」任何概念。

## 9. 风险与遗留

1. **`client` 角色放开 `leads.read` 的边界**：需确认「客户只看自己的询盘」还是「看全站询盘」，涉及 `canRead` 的租户/归属过滤，一期需先定口径。
2. **`publishAll()` 门面**：不改变 `packages/domain` 语义，但需确认「单条发布 + 重建」的组合在 RFQ/报价（`022/023` 迁移后）场景下无副作用，上线前用 `.runtime/smoke-*.mjs` 复跑。
3. **双模式切换的状态**：`localStorage` 存偏好，需注意不同浏览器/账号共用同一台机器的场景（建议按 `user id` 存而非全局）。
4. **不在本期范围**：多租户数据隔离、付费能力分级（不同套餐显示不同功能）——若未来按套餐卖，可在 `roleGroups` 之上再加一层「套餐→组」映射。
